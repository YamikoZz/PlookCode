# PlookCode: A Code Model Trained From Scratch on a Hobby Budget

**Technical report, version 0.1 (2026-11-08)**, YamikoZz, with AI coding assistants
Repository: https://github.com/YamikoZz/PlookCode (MIT License)

> Status: interim report. The 20M-parameter results are final and independently re-checked. The 193M-parameter
> model is being trained at the time of writing, and **this report contains no results for it**. Section 9 will be
> filled in once its evaluation is complete.

## Abstract

PlookCode is a code-writing language model and agent built by one person. Every model weight is trained from
random initialization. No pretrained or open-weight checkpoints are used. The target use is "vibe coding": the
user describes a function in English, the model writes code, and a local runner executes tests and asks the model
to repair failures. We describe the architecture, data, and training of three model generations (6.9M, 20.5M and
193M parameters), along with a procedural evaluation suite whose test-based scoring we revised after external
review.

The 20.5M model reaches **66.8% greedy pass@1 (131/196)** on our in-domain suite. That score breaks down to 79.9%
on task families seen during fine-tuning and **0% (0/32) on held-out families**. In other words, at this size the
model reproduces patterns it has seen and does not generalize. An independent re-run of the recorded answers
reproduced all 196 pass/fail outcomes. The full 20M pipeline cost about 3.6 Colab compute units (≈12 THB). The
193M run is budgeted at about 97 units (≈330 THB).

## 1. Goals and constraints

The project is defined by a small set of rules (see `CLAUDE.md`):

1. **No foreign weights.** Only datasets may be downloaded. Tokenizer and model are trained from scratch.
2. **No execution of downloaded dataset code on the host.** Dataset code is checked by parsing or allow-listing,
   or run in a sandbox.
3. **Training data** may include public AI-generated datasets whose license allows it. This rule was relaxed on
   2026-11-08; before that date only program-generated, verifiable data and public human data were used.
   Licenses and terms are checked per source, evaluation sets are never trained on, and Claude is not used for bulk
   data generation.
4. **No refusal behaviour is trained in.** Fine-tuning data contains no "I can't help with that" examples.
5. **Low cost.** Training runs on Google Colab pay-as-you-go GPUs. The finished model must run on a home PC.
6. **Honest reporting.** Every number is either measured or explicitly marked as an estimate.

We do not aim to compete with large open models. The research question is how far a single person can get on a
hobby budget, and which design choices matter most at small scale.

## 2. Model

Decoder-only Transformer ("v2"), implemented in `localbrain/model.py`:

| Component | Choice |
|---|---|
| Positional encoding | RoPE |
| Normalization | RMSNorm (pre-norm), QK-Norm on attention queries/keys |
| MLP activation | ReLU² (`relu(x)²`) |
| Embeddings | input embedding tied to output head |
| Initialization | output projections of attention and MLP initialized to zero |
| Attention (193M) | grouped-query attention, 16 query heads / 4 KV heads |
| Optimizer | Muon for 2-D matrices inside blocks; AdamW for embeddings/head and norms (`localbrain/train.py`) |
| LR schedule | warmup–stable–decay (WSD) |

| Generation | Params | Layers | Width | Heads | Context | Vocab | Precision |
|---|---|---|---|---|---|---|---|
| G1 (Thai chat) | 6,895,616 | 6 | 256 | – | 256 | 8,192 | FP32 |
| G2 (code) | 20,454,784 | 8 | 384 | 6 | 512 | 16,384 | FP32 |
| G3 (code) | 192,973,824 | 16 | 1,024 | 16 (KV 4) | 2,048 | 16,384 | BF16 |

## 3. Data

**Tokenizer.** BPE with a 16,384-entry vocabulary, trained by us on our own corpus (SHA-256 prefix `ff5386c5`).
G2 and G3 share it.

**Pretraining corpus.** Code from `codeparrot/github-code-clean` and English from FineWeb-Edu (sample-10BT).

| | G2 | G3 |
|---|---|---|
| Source shards | 8 code + 1 English | 110 code + 8 English |
| Train tokens | 319,223,829 | 4,002,776,765 |
| Validation tokens | – | 31.7M |

**Supervised fine-tuning (SFT).**
- G2 used 69,763 training examples: Dolly-15k, OpenAssistant oasst2 multi-turn (11,750 pairs), 4,258 verified
  arithmetic items, 115 greetings, 230 multi-language and math-via-code items, and procedurally generated coding
  tasks from 41 task families.
- G3 will add 228,453 examples imported from public AI-generated code datasets (`scripts/import_code_sft.py`):
  BigCode self-oss-instruct-sc2 (ODC-By, execution-filtered), OpenCoder opc-sft-stage2 educational and McEval
  subsets (MIT), and NVIDIA OpenCodeInstruct (CC-BY-4.0; 2 of 50 shards, only rows whose recorded tests all pass).
  Datasets generated by proprietary models were excluded because of their terms of use.

**Decontamination (G3 SFT).** A row is dropped if its question shares a 13-word sequence with any HumanEval or MBPP
task text, if it contains an entire short MBPP task, or if it mentions a function name from our held-out task
families. Punctuation is ignored, and solutions are not compared.

On the first pass we also compared solutions using punctuation-level 10-grams. That wrongly removed about 93K rows,
because boilerplate such as `for i in range(1, n + 1):` appears in all code. We corrected the filter before using
the data.

The final filter catches 164/164 HumanEval prompts and 500/500 MBPP test prompts, including prompts embedded inside
longer text. Removed: 1,587 eval-overlapping rows, 913 held-out-name rows, 26,323 duplicates and 24 refusals.

Language balance is very skewed: 223,612 Python examples against fewer than 1,300 each for Lua, JavaScript,
TypeScript, C and C++. Additional Lua/TS/JS data is being generated, and the SFT mixture will cap Python.

## 4. Training

| | G1 | G2 | G3 (planned / measured) |
|---|---|---|---|
| Hardware | GTX 1650 SUPER (home) | Colab T4 | Colab L4 (22 GiB) |
| Pretrain | none | 24,000 steps × 32 × 512 = 393M tokens | 7,600 steps × 524,288 = 3.98B tokens |
| Anneal | – | 4,000 steps (≈33M tokens) | planned (python-edu) |
| SFT | 6,000 steps | 1,200 steps | planned |
| Speed | – | ≈1.05 s/step | **23.6–23.9 s/step measured** |
| Peak memory | 315 MiB | ≈8.8 GiB | **9.5 GiB measured** (micro-batch 4 × accumulation 64) |

Choices for G3, based on smoke tests on the L4:
- Micro-batch 16 ran out of memory (21.9 of 22 GiB).
- Micro-batch 8 used 16.3 GiB and was only about 1% faster than micro-batch 4, so the GPU is compute-bound.
- In a 60-step smoke test, loss fell from 17.7 to 4.59.

Checkpoints are written every 50 steps to Google Drive, so the run can resume across Colab sessions.

## 5. Evaluation method

**Suite.** `localbrain/tasks.py` defines 49 procedural task families. Each family has a reference implementation
that generates test cases, plus several phrasings. Eight families are held out from SFT data generation ("unseen"):
`range_diff`, `pairwise_diff`, `longest_word`, `sum_digits`, `clamp`, `second_largest`, `count_char` and
`is_sorted`. The benchmark samples 2 tasks per family per language (Python, JavaScript), for 196 tasks. Each task
has 8 test cases.

**Scoring.** Generated code runs in a separate process (`localbrain/runner.py`) in an empty temporary directory,
with a timeout, an output cap, an AST allow-list (Python) and a token block-list (JavaScript), and an audit hook
that blocks file, network and process access. A task passes only if every test passes. No model judges another
model's answer.

**Metrics.**
- Greedy pass@1.
- pass@8 at temperature 0.8.
- Since revision `1792f84`, `agent_pass`. Here the agent loop (`solve()`: sample, test, repair) sees only 3 public
  tests as feedback. The chosen code is then scored on all 8 tests, and no solution cache is used.

**Revisions after review (2026-11-08).**
1. The example shown in each prompt was previously one of the scored tests. It is now drawn from outside the scored
   set. The 196 test sets themselves are unchanged and all still have 8 cases.
2. Model-only and agent-assisted scores are reported separately.
3. All sampled answers are now stored, so pass@k can be re-checked.
4. A unit test checks the agent mode with a solver that memorizes only the public tests; it must score 0. A
   deliberately broken scorer that used only the public tests made this test fail, as intended.

## 6. Results: G2 (20.5M)

| Split / language | Greedy pass@1 | pass@8 |
|---|---|---|
| seen / Python | 63/82 = 76.8% | 67/82 = 81.7% |
| seen / JavaScript | 68/82 = 82.9% | 68/82 = 82.9% |
| unseen / Python | **0/16 = 0%** | 2/16 = 12.5% |
| unseen / JavaScript | **0/16 = 0%** | 0/16 = 0% |
| **Total** | **131/196 = 66.8%** | 137/196 = 69.9% |

These scores are model-only, with no agent assistance. They were measured with the pre-revision prompts (Section
5), so they are not directly comparable with future scores.

Validation loss: pretrain 2.006, SFT 1.741. These numbers are comparable only within this project, because they
depend on our tokenizer.

Qualitative chat tests passed simple tasks (`is_even`, a Lua `add` function). They failed arithmetic stated in
words ("7 + 8" → 9), string reversal in JavaScript, and casual conversation.

G1 (6.9M, Thai, SFT only) reached a test loss of 4.25, but its answers were mostly incoherent. That outcome is why
later generations added a pretraining stage and narrowed the domain to code.

**Interpretation.** G2 has learned the task templates it was fine-tuned on and does not transfer to new task
families. Raising the unseen-family score is the main success criterion for G3.

## 7. Independent review

We asked four external AI systems to audit the repository and checked every claim they made against the code.

| Reviewer | Accurate findings | Errors |
|---|---|---|
| Local GPT-based agent with file access (read-only) | Re-ran all 196 recorded greedy answers and reproduced 131/196 with no mismatch. Found that pass@8 was not re-checkable and that a new agent-mode unit test was too weak. | none found |
| ChatGPT | 66.8% is model-only. Reconstructed the per-split counts. Found that the prompt example leaked into the scored tests. | none found |
| Gemini | Correctly described most of the architecture and the test runner. | Claimed SwiGLU (the model uses ReLU²). Claimed the score was agent-assisted. Claimed 200M results exist. |
| DeepSeek | Correctly described the runner safeguards. | Claimed the score was agent-assisted and seen-only. |

Every accurate finding led to a fix (Section 5). The re-check wording we use: *"The original pass@1 of 66.8%
(131/196) was re-checked by re-running the recorded greedy answers against the original test cases, and every
result matched."*

Our **estimate** (not a result) for G3 is roughly 2–6% greedy pass@1 on HumanEval. It is based on its size and on

this scale.

## 11. Limitations

- The in-domain suite contains small single-function tasks. Most families resemble the SFT templates.
- G2 scores were measured before the evaluation revision. The checkpoint is not published, so outside parties
  cannot regenerate the answers. They can only re-check the recorded ones.
- The agent's project-patching ability has only been tested with scripted patches. G2 could not write a working
  patch on its own.
- Lua, TypeScript, C and C++ cannot yet be verified automatically by the runner.
- The rule-3 relaxation means G3 SFT data is partly AI-generated, from open models only, with licenses checked.

## 12. Reproducibility
